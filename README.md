# L3X

A confidential order-book exchange rollup on Aztec. [`SPEC.md`](SPEC.md) is the design. This repository holds phase P0 (SPEC.md §15): the `rollup-on-aztec` proof pipeline ported to Aztec v6 with its gaps closed, plus a Bridge contract that settles batches.

Toolchain: Aztec **6.0.0** (`.aztecrc`), with its bundled `aztec-nargo` (Noir 1.0.0-rc.3) and `aztec-bb`, and Node 24 running the TypeScript scripts directly. The spec targets 6.1.0, but neither the installer nor npm publishes its toolchain yet. The v6.0.0 proof-type and size constants match those checked for v6.1 in SPEC.md §3.

## Layout

| Path | Contents |
| --- | --- |
| `circuits/l3x_types` | Shared constants, domain separators, Poseidon2 sponge, `AggOutput`, `BatchHeader` |
| `circuits/client_auth` | P-lane client circuit: knowledge of the secret behind an account's auth binding, authorizing `msg` |
| `circuits/agg_app` | Chonk app: verifies 10 client proofs against the pinned client VK and folds the first `count` |
| `circuits/{init,tail,hiding}_kernel` | IVC kernels: OINK, HN, HN_FINAL, each pinning its predecessor's VK hash |
| `circuits/tube` | Verifies the Chonk proof against the pinned Chonk VK; proved as RollupHonk (no ZK) |
| `circuits/padding` | Empty segment; bb's root verifier needs exactly two IPA claims |
| `circuits/root` | Verifies tube and padding with `verify_root_rolluphonk_proof`; binds the batch header; outputs `H(header)` |
| `circuits/rogue_app` | Adversarial fixture for the VK-substitution tests; never deployed |
| `circuits/vendor/bb_proof_verification` | Vendored from aztec-packages v6.0.0 (Apache-2.0) |
| `contracts/bridge` | `L3XBridge`: priority queue, `settle` (private verify) → `_apply` (public checks) |
| `scripts/src` | `build.ts`, `prove.ts`, `vk_substitution.ts`, `settle.ts`, and `pipeline.ts` (batch prover) |
| `scripts/out` | Generated: VK manifest, batch, measurements and settlement reports (git-ignored) |

`*/src/pinned.nr` files are generated by `build.ts` and are not hand-edited.

## Running

```bash
cd scripts && npm install
```

```bash
npm run build:circuits
```

The build compiles in dependency order and pins each child VK hash into its parent. It writes `scripts/out/manifest.json`, which includes the configuration hash and the root VK hash.

```bash
npm run prove
```

This proves one synthetic batch natively. It writes `scripts/out/batch-1.json` and `scripts/out/measurements.json`.

```bash
npm run vk-substitution
```

This runs the G2 negative tests: a rogue app under `init_kernel`, and a padding proof in the root's tube slot. Both must be rejected.

```bash
npm run settle
```

This runs the P0 exit test on an in-process 6.0.0 local network, with real client-side proofs.

```bash
cd contracts && aztec compile
```

This compiles the Bridge contract.

## P0 status

See SPEC.md §14 for the measured numbers.

| Item | State |
| --- | --- |
| G1: tube → root → contract | Done. Root verifies two RollupHonk proofs and closes IPA; the root proof is UltraHonk ZK. |
| G2: VK pinning | Done. Every recursive verification pins its child VK hash; both substitution tests rejected. |
| G3: Bridge state | Done (P0 subset): state root, batch number, priority queue with `T_force`, time bounds with `T_lag`, DA hash, replay protection. |
| G4: shape | Partial: occupancy 0–10 with real proofs in every slot; one segment plus padding. Merge tree not built. |
| G5: v6 constants | Done for 6.0.0; Chonk proof length and layout checked at runtime. |
| M1–M5 | Measured (SPEC.md §14). Not yet measured: the UltraHonk-in-UltraHonk comparison for M1, and the cost of a full 4,096-field DA payload for M5. |
| P0 exit test | Passed on a 6.0.0 local network with the PXE prover and node `realProofs` on. The Bridge was deployed and two priority requests queued. Batch 1, proved over the on-chain queue, settled through a client-proved transaction (checkpointed, success), and the on-chain tip matches the header. Negative checks: a replayed settlement is rejected by `_apply` ("stale state root"). A forged batch-2 header that passes every public check, paired with batch 1's proof, is rejected while the settlement transaction is being proved ("Failed to verify the generated proof!"). Report: `scripts/out/settlement.json`. |

Not in P0: custody (C1), withdrawals, desert mode, exchange state, the merge tree, `DelayedPublicMutable` configuration (P0 uses `PublicImmutable`), and VK trees (P0 pins constants).

## Caveats

- The local network settles epochs synthetically, so a receipt status of `proven` there does not mean an epoch proof was verified. What is real in `settle.ts`: the settlement transaction's client-side Chonk proof, which includes verifying the root proof in-circuit, and the node's check of transaction proofs (`realProofs`).
- Timings come from one laptop run each and are not benchmarks.
- The P0 auth circuit and the "accounts root" stub stand in for real exchange logic.
